## How targets are run

Each target is dispatched through the documented env-var mechanism in
`main.py`:

```bash
QT_QPA_PLATFORM=offscreen \
  SCENE_RIPPER_RUNTIME_SMOKE_TEST_TARGET=<target> \
  python main.py
```

`main.py` reads `SCENE_RIPPER_RUNTIME_SMOKE_TEST_TARGET`
(`RUNTIME_SMOKE_TARGET_ENV`), calls `run_runtime_smoke_target(<target>)`, and
exits 0 on success / non-zero on failure. Each target provisions its own
temporary media and cleans up after itself.

## The one failure: `imports`

`imports` fails locally because **libmpv is not installed** on this machine.
The target does a bare `import mpv`, which triggers `ctypes.util.find_library`
to locate `libmpv`:

```
OSError: Cannot find libmpv in the usual places.
```

`ctypes.util.find_library('mpv')` returns `None` here. Homebrew has the mpv
**player app** installed (`/opt/homebrew/Cellar/mpv/0.41.0_2`) but not the
`libmpv` **shared library** the Python `mpv` binding needs.

This is expected for a bare source checkout and does **not** indicate a problem
with the smoke framework or the four new targets. The frozen macOS app bundles
`libmpv`, so `imports` passes in the release pipeline. To reproduce a pass
locally, libmpv must be discoverable by `ctypes` (e.g. an `mpv`/`libmpv` build
that installs the dylib into a standard search path).

## New targets — provisioning & assertions

All four new targets follow the module's existing conventions: lazy imports of
heavy/optional modules inside the target body, self-contained temp media via
`tempfile.TemporaryDirectory`, and `RuntimeError` with a specific message on any
failed assertion. They reuse the existing `_create_synthetic_scene_video`
helper (a 96×72 MP4 of three solid-color scenes with hard cuts).

- **`analyze-clip`** — Exercises the non-ML analysis paths
  (`extract_dominant_colors` + `get_average_brightness` from
  `core/analysis/color.py`) on the first (blue) scene of the synthetic clip.
  Asserts dominant colors are non-empty and every RGB channel is in `[0, 255]`,
  and that brightness is in `[0.0, 1.0]`.

- **`sequence-build`** — Runs scene detection on the synthetic clip, builds a
  `Project`, and calls `project.add_to_sequence(...)` for the first few clips.
  Asserts the sequence exists, has the expected clip count, that each
  `SequenceClip` references a real source clip with a positive-duration trim
  range, that clips are laid end-to-end (each `start_frame` follows the prior
  clip's end), and that total timeline duration is positive.

- **`render-short`** — Detects clips, builds a sequence, sets fps from the
  source, asserts the timeline is ≤5s, then renders through
  `core.sequence_export.export_sequence(...)` to a temp MP4. Asserts the output
  file exists and is non-empty, then runs bundled **ffprobe** to confirm the
  output parses, contains a video stream, and reports a positive duration.

- **`mcp-stdio`** — Launches the MCP server as a subprocess over stdio
  (prefers the `scene-ripper-mcp` console entry point; falls back to
  `python -c "from scene_ripper_mcp.server import main; main()"` for a source
  checkout). Speaks newline-delimited JSON-RPC directly over the pipes: sends
  `initialize`, asserts a negotiated protocol version, sends
  `notifications/initialized`, then calls the read tool `list_projects` against
  a temp directory. Asserts the tool reports `success: true` with `count` and
  `projects` keys, then terminates the subprocess cleanly. Every stdout read is
  bounded by a watchdog-thread timeout so a hung server can't wedge the run.

## Notes for maintainers

- **`mcp-stdio` deliberately does not use `python -m scene_ripper_mcp.server`.**
  Running the server as `__main__` creates a *second* `scene_ripper_mcp.server`
  module when the tool packages do `from scene_ripper_mcp.server import mcp`;
  the `@mcp.tool()` decorators then register on a different `mcp` instance than
  the one `main()` runs, and the server exposes **zero tools** (observed:
  `"Unknown tool: list_projects"`). The console script and the `-c` import both
  load the module under its canonical name and register all 57 tools correctly.
  This is a pre-existing `-m` launch hazard, surfaced (and routed around) here.

- Adding the four targets changes the tuple returned by
  `get_runtime_smoke_targets()`, which the guardrail test
  `tests/test_runtime_smoke.py::test_runtime_smoke_targets_are_stable` asserts
  exactly. That test must be updated to the new 9-target tuple (and ideally gain
  pass-tests for the four new targets, matching the existing
  `test_*_runtime_smoke_passes` pattern).
